# Feature Specification: Signal identity re-base — stable GUID key + cosmetic name + generated constants

**Feature Branch**: `032-signal-identity-rebase`

**Created**: 2026-07-07

**Status**: Implemented 2026-07-07 (graphcore 0.33.0). FR-009 deferred (see note). All decisions D1–D5 resolved.

**Input**: Design discussion (2026-07-07). Starting point: an audit found that a `SignalName` asset's produced
string falls back to the asset file name when its `_name` field is empty, so renaming the file silently
changes the raised string and breaks saved has-fired history (`GetAllRaisedSignals` persists the string).
Digging deeper revealed the file-name drift is only one leak of a wider problem: a signal's identity is an
**ungoverned human string shared across four surfaces with no single source of truth**, and `SignalName`
sits on a *third* identity model (human-string) inconsistent with `CollectionEntry`/`CollectionName`
(stable GUID + cosmetic `Title`, since graphcore 0.30.0) and with parameters (raw string). The endpoint is
to re-base signal identity onto the same GUID model the collections already use, and bridge the pure-code
surface with generated constants.

**Constraints agreed up front**: the ecosystem is unpublished; the only consumer is the author's test
project, which will be regenerated by hand. **No migration, compat shim, or save-history preservation is
required — this is a clean break.**

---

## Problem statement

A signal's identity is a bare human-readable string that lives, with no single source of truth, on four
surfaces:

1. **Host C# code** — `driver.RaiseSignal("advance")`: a raw literal. No autocompletion, no compile check;
   a typo is a silent no-op (the awaiting node never wakes, no error).
2. **Raiser side in graphs** — `RaiseSignalAction` → a `SignalName` asset (governed) *or* a raw string.
3. **Awaiter side in graphs** — `BaseNodeData.AwaitSignalName` / `AwaitSignals` → a `SignalName` asset *or* a
   raw string.
4. **Persistence** — `BaseContext.GetAllRaisedSignals` stores the raised string into a `GraphRunSnapshot`.

`SignalName` was meant to be the single source of truth that kills typos, but it fails on three counts: it
does not govern surface (1) at all; its own identity drifts when the asset file is renamed (`Name` falls
back to `base.name`); and it permits raw-string bypass on (2)/(3). Closing only the file-name drift fixes
one leak on one surface.

The decisive consequence of a *string* identity: **renaming a signal is a silent data-breaker.** Change the
name and every stored save, every raw await, and every code literal that used the old string breaks — most
of them silently.

---

## Endpoint

`SignalName` adopts the **exact identity model `CollectionEntry`/`CollectionName` already use**:

- A **stable GUID** (`_id`, assigned once in `OnEnable`, never editable) is the **primary key** — the string
  actually raised, awaited, matched, and stored in saves.
- `_name` becomes a **cosmetic display label** (like `CollectionEntry.Title`): human-readable, editable,
  used for editor tooling and as the seed for the generated identifier. **It is never the runtime key.**
- The pure-code surface is bridged by **generated constants**: a `GraphSignals.PlayerInteracted = "<guid>"`
  static class generated from the `SignalName` assets, so host code references a compile-checked symbol whose
  value is the GUID.

This makes **renaming a signal free**: editing `_name` never touches the GUID, so every await, raise, and
save keeps matching (the data never breaks); only the regenerated constant *identifier* changes, so pure
code that referenced the old identifier **fails to compile — loudly and early — pointing you at every site
to update**. It also collapses the three-identity-models inconsistency: signals, collections (and, later,
parameters) all sit on one GUID + cosmetic-label model, and GUID keys become human-readable in editor
tooling through the **existing** `ContextKeyLabelRegistry` / `IContextLabelResolver` seam (the same one that
already labels collection GUIDs in the Context Watch window).

## User Scenarios & Testing *(mandatory)*

**Actors**
- **Graph author** — wires raises/awaits in graph assets, references `SignalName` assets.
- **Host integrator** — game C# code that raises signals into a running graph.
- **Debug/prototyper** — quickly raises a signal by hand while iterating.

### User Story 1 - Renaming a signal never breaks the data (Priority: P1)

An author references the same `SignalName` asset on a `RaiseSignalAction` and on a node's await. Execution
matches them on the asset's stable GUID. The author later renames the signal's display name (and/or the asset
file) for clarity. Every raise, await, and saved has-fired record keeps matching — the rename changed only the
cosmetic label, never the key.

**Why this priority**: This is the core value — it is the property the whole re-base exists to deliver, and
the one a human-string identity fundamentally cannot provide.

**Independent Test**: A `SignalName` asset drives a raise and an await; run and assert they match. Change
`_name` (and rename the asset file); re-run and assert they still match; assert `Key` (the GUID) is unchanged
across the rename.

**Acceptance Scenarios**:
1. **Given** a raise and an await both referencing signal asset S, **When** the graph runs, **Then** the await
   resumes on the raise, matched on S's GUID.
2. **Given** the same setup, **When** S's `_name` is edited and its asset file renamed, **Then** raise/await
   still match and S's `Key` is unchanged.
3. **Given** a save captured with S raised, **When** S is renamed and the save is restored, **Then**
   `HasSignalBeenRaised` for S is still true (the save stored the GUID, which did not change).

---

### User Story 2 - Pure code references a compile-checked signal (Priority: P1)

Host code that is not wired to a `SignalName` asset in the inspector raises a signal through a **generated
constant** — `driver.RaiseSignal(GraphSignals.PlayerInteracted)` — instead of a raw literal. The identifier
is compile-checked and autocompleted; the value is the signal's GUID, so it matches asset-based awaits.
Renaming the signal regenerates the constants; code that used the old identifier fails to compile.

**Why this priority**: This is the surface a human-string identity can never secure, and the reason the GUID
re-base must ship *with* codegen rather than deferring it — once the key is a GUID, a raw literal can no
longer interoperate with an asset await, so the generated constant is the load-bearing bridge, not a
convenience.

**Independent Test**: Generate constants for a project with a `SignalName` "Player Interacted"; assert a
`GraphSignals.PlayerInteracted` constant exists whose value equals the asset's GUID; assert raising via the
constant wakes a node awaiting that asset.

**Acceptance Scenarios**:
1. **Given** a `SignalName` asset, **When** constants are generated, **Then** a constant exists whose
   identifier derives from its `_name` and whose value equals its GUID.
2. **Given** a node awaiting that asset, **When** host code raises via the generated constant, **Then** the
   node resumes.
3. **Given** the signal's `_name` is changed and constants regenerated, **When** the project recompiles,
   **Then** code referencing the old identifier no longer compiles.

---

### User Story 3 - Raw-string escape hatch stays viable for dynamic/debug use (Priority: P2)

A developer raises a signal by raw string for a quick test or a dynamically-computed name
(`driver.RaiseSignal(someRuntimeString)`), and can author a raw-string await to match it. This path keeps
working — the context signal channel is string-keyed and a literal is just another string — but it is
explicitly **ungoverned and fragile**: no tooling, typos are silent, and (per the islands decision below) it
does not interoperate with asset-based (GUID) awaits.

**Why this priority**: Keeps the low-ceremony dynamic path the current API already offers; it must not be
removed, only demoted from "default" to "escape hatch".

**Independent Test**: Raise raw `"foo"` and await raw `"foo"`; assert they match. Raise raw `"foo"` against a
node awaiting a `SignalName` asset whose display name is "foo"; assert (islands decision) they do **not**
match.

**Acceptance Scenarios**:
1. **Given** a raw-string raise and a raw-string await on the same literal, **When** the graph runs, **Then**
   they match.
2. **Given** a raw-string raise of a name that coincides with an asset's display name, **When** a node awaits
   that asset, **Then** they do not match (asset awaits key on the GUID, not the display name).

---

### User Story 4 - GUID keys stay human-readable in tooling (Priority: P2)

An author inspects a running context (Context Watch) or a save file's signal history. GUIDs are shown with
their signal's display name via the existing label-resolver seam, so the opaque keys are legible during
debugging.

**Independent Test**: Register a signal label resolver; assert Context Watch shows the display name (GUID as
tooltip) for a raised signal GUID.

**Acceptance Scenarios**:
1. **Given** a raised signal GUID and a registered resolver, **When** Context Watch renders it, **Then** it
   shows the display name with the raw GUID available as a tooltip.

## Requirements *(mandatory)*

**Runtime identity**
- **FR-001**: `SignalName` MUST expose a stable `Key` GUID assigned once in `OnEnable`, never editable, never
  derived from the asset file name (mirrors `CollectionEntry`/`CollectionName` since 0.30.0).
- **FR-002**: `SignalName._name` MUST become a cosmetic display label (`Title`-equivalent), never the runtime
  key; falls back to the asset name when empty for display only.
- **FR-003**: `(string)SignalName` (implicit operator) MUST return the GUID `Key`, so `RaiseSignalAction`,
  `AwaitSignals`, and any asset-based surface key on the GUID.
- **FR-004**: The stable-GUID duplicate detector (`StableIdDuplicateDetector`, via `IStableGuidIdentity`)
  MUST cover `SignalName` — duplicating the asset must regenerate the copy's GUID, exactly as for the other
  identity types.

**Codegen (pure-code bridge)**
- **FR-005**: A generator MUST produce a static constants class from the project's `SignalName` assets, each
  constant's identifier derived from `_name` (sanitized to a valid C# identifier) and value equal to the
  asset's GUID.
- **FR-006**: Regeneration MUST be triggerable on demand via a menu command (`Faolline ▸ Signals ▸ Generate
  Constants`). Auto-trigger on asset import is deferred (D3).
- **FR-007**: Identifier collisions (two signals whose `_name` sanitizes to the same identifier) MUST be
  detected and reported, not silently merged.

**Escape hatch & tooling**
- **FR-008**: The raw-string paths (`RaiseSignal(string)`, `AwaitSignalName` raw field) MUST keep working as
  an ungoverned literal channel; per the islands decision (D1) they do not interoperate with GUID-keyed asset
  signals.
- **FR-009**: A `SignalName` `IContextLabelResolver` SHOULD be registered so Context Watch renders signal
  GUIDs with their display name (parity with collection GUID labelling).
  **→ DEFERRED (2026-07-07): the Context Watch window does not currently surface signals at all (only
  parameters and collections), so there is no signal GUID to label yet. Revisit if/when signal history is
  added to Context Watch.**

**Non-goals for this feature**
- Parameter identity (raw string) is **out of scope** — a separate, later item, though it is the natural next
  application of the same model.
- No collection changes.
- The deeper "capability composition over storage shape" rework is out of scope; this feature is the identity
  re-base only.

## Key design decisions — to resolve before implementation

- **D1 — Islands vs dual-key. → RESOLVED: islands (2026-07-07).** Asset signals key on the GUID only; raw
  signals key on literals only; the two channels do not cross. Clean, and it keeps the save's rename-safety
  intact (a save only ever stores GUIDs for governed signals). Accepted cost: a raw debug-raise cannot wake
  an asset await — use the generated constant instead. (Dual-key — an asset await also listening on its
  display name — was rejected: the raised *name*, not the GUID, would land in the save history,
  re-contaminating persistence with the rename-fragility this feature removes.)

- **D2 — Generated constant *symbol* scheme (NOT the GUID).** A generated constant has two parts: its C#
  **symbol name**, derived from `_name` so code reads legibly (`GraphSignals.PlayerInteracted`), and its
  **value**, which is the asset's **GUID** (needs no scheme — it is the runtime key verbatim). D2 is only
  about the symbol name: `_name` → C# identifier (PascalCase, strip/replace invalid chars, prefix when it
  starts with a digit — exact transform TBD), plus the collision policy (FR-007: two `_name`s that sanitize
  to the same symbol → **blocking error + report**, never a silent merge or an auto-suffix that would mask a
  real duplicate of intent). Renaming `_name` changes the symbol (breaking old code at compile) but never the
  value/GUID (data keeps matching) — which is exactly the free-rename property.
  **→ RESOLVED (2026-07-07): symbol from `_name` (PascalCase sanitize), value = GUID, blocking error on
  symbol collision.**

- **D3 — Codegen source, location, trigger, namespace. → RESOLVED (2026-07-07):**
  - *Source*: **scan** all `SignalName` assets via `AssetDatabase.FindAssets("t:SignalName")` — zero
    ceremony, matches `StableIdDuplicateDetector` and the localization build. (A catalog for grouping is
    deferred until a "too many signals in one flat class" need appears.)
  - *Trigger*: **menu command only** for v1 (`Faolline ▸ Signals ▸ Generate Constants`). Auto-regen on
    import is deferred (avoids constant regeneration churn; parity with the menu-driven localization build).
  - *Output location + namespace*: **fixed default, override deferred** — default `Assets/Generated/GraphSignals.cs`,
    no namespace (or a single fixed one). Configurability via a settings asset is deferred; not worth
    introducing a `SignalSettings` asset in v1.
  - graphcore ships the **generator** (editor tool); the generated class lives in the **consumer** project
    (each game has its own signals) and is pure `const string` — zero dependencies. This repo has no
    on-disk `SignalName` assets, so nothing is generated here; the repo tests the generator's *logic*
    (asset set → expected output), not a committed file.

- **D4 — `AwaitSignalName` (raw string) vs `AwaitSignals` (asset list). → RESOLVED (2026-07-07):** the raw
  string field stays as the literal escape hatch (islands); the asset list yields GUIDs via FR-003. No change
  to `BaseNodeData`'s serialized shape beyond `(string)SignalName` now returning the GUID.

- **D5 — Test-created signals. → RESOLVED (2026-07-07):** add a `SignalName.CreateForTest(displayName)`
  factory (or equivalent) so the ~9 test/sample sites keep a readable creation call; they key on the GUID
  like everything else. Clean break — no back-compat constraint. (The factory belongs to the test seam, not
  the shipping authoring surface.)

## Testing strategy

Headless EditMode, TDD as usual:
- Identity stability: `Key` is a GUID, unchanged across `_name` edit and asset-file rename (US1).
- Duplicate detection covers `SignalName` (FR-004).
- Codegen: constant identifier derives from `_name`, value equals GUID; regeneration after a rename changes
  the identifier; collision is reported (US2, FR-005/007).
- Islands behavior: raw↔raw matches, raw↛asset (US3, D1).
- Label resolver renders the display name for a signal GUID (US4, FR-009).

## Rationale trail (why this shape and not the alternatives)

- **Why not "name = stable identity" (freeze the file-name into `_name`, keep it the key)?** Non-breaking and
  shippable now, but leaves signals on a different identity model than collections, keeps pure-code literals
  fragile, and — decisively — every future rename remains a silent data-breaker. The GUID model makes rename
  free forever at a one-time (here: zero, unpublished) cost.
- **Why not runtime name→GUID resolution for pure code?** It reintroduces exactly the ungoverned-string
  problem at runtime (name-collision ambiguity, silent typos, a catalog load) — codegen done at the worst
  place. Generated constants move the same resolution to compile time, with safety.
- **Why ship codegen now instead of deferring it?** Once the key is a GUID, a raw literal can no longer
  interoperate with an asset await, so the generated constant is the load-bearing bridge for pure code, not a
  convenience. The GUID re-base and codegen are one coordinated change.
